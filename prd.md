# Product Requirements Document (PRD) - RideWise Assist

## 1. Product Overview
**RideWise Assist** is a conversational AI designed for a two-wheeler and EV rental company. Its purpose is to autonomously answer queries regarding bookings, payments, rental rules, and damage penalties. It sources its answers from the company's SQLite operational database and 5 unstructured policy documents.

## 2. Target Personas
1. **Registered Customer:**
   - **Needs:** Information about their own bookings, payment status, account details, and public rental policies.
   - **Restrictions:** Must not be able to access data belonging to other customers or internal operational statistics.
2. **Support Agent:**
   - **Needs:** Operational information across the entire business to resolve issues (e.g., querying all late returns today).
   - **Restrictions:** Still bound by reasonable AI safety guidelines, but has full data visibility.

## 3. Core Features
### 3.1 Authentication & Role Management
- The UI must allow the user to select their role (Customer vs. Support Agent).
- Customers must be able to identify themselves easily using a **10-digit mobile number** (or `customer_id`). The system will map the mobile number to the internal ID seamlessly.

### 3.2 Chat Interface
- A clean, functional, and modern chat window.
- Must support typing indicators while the LLM orchestrates actions in the background.
- Must render Markdown (for tables, bold text, and lists) generated by the LLM.

### 3.3 Dynamic Orchestration
- The assistant must autonomously decide whether a query requires database access (structured), document retrieval (unstructured), or both.
- **RAG Engine:** Processes and queries the 5 provided PDFs for rule-based questions (e.g., cancellation policies).
- **Text-to-SQL Engine:** Generates SQL to query `ridewise.db` for operational data.

### 3.4 Strict Access Control
- Queries generated by the LLM must be intercepted and validated.
- If the user is a Customer, the system must enforce a hard filter (`WHERE customer_id = '...'`) before executing any SQL to prevent data leaks.

## 4. Non-Functional Requirements
- **Setup Time:** The entire application (frontend + backend) must be runnable locally in under 10 minutes following the `README.md`.
- **Accuracy:** Zero hallucinations. The assistant must state "I don't know" if the data is unavailable.
- **Robustness:** Must handle invalid SQL generation by allowing the LLM to self-correct during the orchestration loop.
